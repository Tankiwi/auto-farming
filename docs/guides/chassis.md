# 底盘电机分步测试

更新：2026-10-19。依据：[实测与限制](../reports/2026-10-19-motor-test.md)。本轮只有 1 路主动驱动产生反馈动作，非目标编码器也有变化；用户随后明确实际为地面测试，可能存在被动滚动，不能用悬空隔离判据认定故障。四电机尚未逐路验收；下面脚本仍按悬空测试设计，代码未因现场更正而修改。

## 环境与前提

Jetson 宿主机 Python 3、pyserial、`fuser`，不需要 ROS 或 Docker。用户每轮动作前确认四轮稳固悬空、周围清空、无负载，现场能立即断电。电机/编码器编号不直接等同左前、右前等位置。当前历史连接是 `jetson@10.253.197.6`，使用前复核；设备别名 `/dev/myserial`，115200。

脚本源码：[motor-check.py](../../modules/chassis/motor-check.py)；本次部署在 `/home/jetson/farm-tools/motor-check.py`。默认不发运动指令。遇未知版本、串口占用、静止漂移、反馈缺失或校验问题应停止排查，不擅自结束其他程序。

在 **Jetson Bash** 先运行只读检查：

```bash
python3 /home/jetson/farm-tools/motor-check.py
```

预期 `status=read-only`、固件 `[3,5]`、有足够新鲜编码器样本、基线范围均不超过 3。失败不得直接执行动作。

## 动作参数与停止

下列为后续单路复测入口，须先完成上述疑点核对与现场确认；不表示本轮其余路已测：

```bash
python3 /home/jetson/farm-tools/motor-check.py --run --clear-confirmed --channel 1
```

默认 ±15 PWM，各 0.5 秒；`--pwm` 仅接受 15、25、35，`--pulse-seconds` 仅接受 0.5、1.0。不传 `--channel` 会计划逐路 1～4，每路正反测试，但任一步失败即结束。脚本不自动加速、重试、恢复出厂或切换车型。

每次脉冲后独立子进程发送三次四路零 PWM；主进程检查新鲜编码器，退出清理再发归零。本轮已观察到归零后的反馈静止，但零 PWM 不能直接等同主动制动、硬件急停或带载停车保证。异常动作、持续嗡鸣/堵转、反馈失联或未停止时立即现场断电；结束 Python/SSH 不能代替目视停止。断电可能使机械臂失去支撑，现场应预留空间。断线、重启、重新上电恢复和故障看门狗尚未验收。

成功必须分别记录协议、目标轮实际动作、非目标轮状态、正反方向及停止。JSON `failed` 时保留数据，不放宽判据制造通过；实际轮位和现场观察另行记录。

## 官方速度接口动作示例

最新状态见[两次用户日志](../reports/2026-10-19-motion-demo-preflight.md)：用户已上传并运行初版和线程修复版，均读回固件 3.5、底板车型 1，动作被前检拒绝；修复版该次正常退出。当前本地新增的显式配置选项尚无设备执行证据，不能记为已配置成 2。旧交付与修复过程保留在报告和变更记录，不作为当前部署状态。

[motion-demo.py](../../modules/chassis/motion-demo.py)面向空旷地面，用原厂 `set_car_motion` 依次请求：前进 0.10 m/s、3 秒；后退 0.10 m/s、3 秒；左旋 0.25 rad/s、2 秒；右旋 0.25 rad/s、2 秒。每步归零后停留 2 秒。按目标速度×时间，单程约 0.30 米、每次旋转约 28.6°，不是实测值，不承诺准确距离或回到起点。

本例不同于上文悬空单轮脚本，不使用“非目标编码器静止”的隔离判据。它仅演示有限时长的速度命令，未实现位置闭环、避障、反馈新鲜度监测或硬件看门狗。不能把命令序列完成当作真机动作验收。

Windows 在仓库根可预览（无需原厂库，不访问设备）：

```powershell
python modules/chassis/motion-demo.py
```

只有再次核对地面周围清空、无负载、机械臂姿态稳妥、有人可立即断电后，才在 Jetson 访问硬件。**原厂 `Rosmaster` 构造会自动开启机械臂全部扭矩**，本示例保留此行为，因此即使底盘尚未运动也存在机械臂影响。上传、配置、运动是三个独立步骤。

### 上传与版本核对

在 **Windows PowerShell** 从仓库根上传；`scp` 会覆盖目标同名文件，若设备文件有另行改动先备份或比较。上传本身不运行脚本：

```powershell
scp modules/chassis/motion-demo.py jetson@10.253.197.6:motion-demo.py
```

本地执行 `Get-FileHash .\modules\chassis\motion-demo.py -Algorithm SHA256`，在 Jetson 执行 `sha256sum ~/motion-demo.py` 比较；已有用户日志没有完成此哈希核对。在 **Jetson Bash** 可先预览：

```bash
python3 ~/motion-demo.py
```

### 显式设置 X3 Plus 车型

本机实物为 X3 Plus，但用户最新日志的底板配置仍为 1。确认适用固件、实物和上述现场条件后，在 **Jetson Bash** 单独选择配置模式：

```bash
python3 ~/motion-demo.py --configure-x3plus --clear-confirmed
```

此命令**会持久写入底板车型 2**，不是只读查询；构造还会开启机械臂扭矩。它不会执行动作计划，也不恢复出厂或改 PID。只接受版本 3.5、原车型 1/2，写入后再次读取，看到 `CONFIGURED: board car_type=2 read back` 才算本次读回成功。若原本为 2 则只再读回，不重复写。失败时停止、不重试；保留日志，不继续运动。掉电保持/回退待实测。

### 执行与停止

仅在读回 2、现场条件仍满足时，在 **Jetson Bash** 另行执行：

```bash
python3 ~/motion-demo.py --run --clear-confirmed
```

`--run` 与 `--configure-x3plus` 互斥。运动模式要求固件 3.5、底板车型 2，不自动修改配置；不符则 ABORTED，不执行非零动作计划。程序使用共享文件锁并拒绝串口占用。`Rosmaster(car_type=2)` 不等于已把底板保存为 2；ROS 环境变量 `ROBOT_TYPE=x3plus` 也与底板持久化配置不同。

速度指令约每 0.1 秒发送一次；各动作结束和执行函数清理时尝试三次零速度；最外层退出清理尝试三次四路零 PWM。可停止的接收会话先等待线程结束，再关闭串口；该适配依赖归档 3.3.1 私有解析入口，升级库后重新核对。收到 Ctrl+C、SIGTERM、SIGHUP 会尝试清理，但进程强杀、主机/串口故障、原厂 setter 吞异常等仍可能使停止请求失效。没有独立看门狗，异常动作或未停止时立即现场断电。

本地预览、四段假对象模拟及四项前检/配置/退出回归通过；回归入口为 `python -B modules/chassis/tests/test-motion-demo.py`。用户日志仅验证修复版一次正常退出和车型读回 1，没有验证新增配置选项、实际前后移动/旋转、速度精度或停车。后续保存配置前后读回、脚本哈希、方向与现场停止观察，再更新设备状态。
